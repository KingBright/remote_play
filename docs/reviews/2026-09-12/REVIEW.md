审查基线：`7abf9f0`。本次优先检查实时收发、音视频队列、macOS 解码资源管理、遥测计算和 Web 会话生命周期；改动保留在工作区，未提交或部署。

## 验证证据

- Rust 工作区 **368 项**测试通过，见 [rust-tests.txt](rust-tests.txt)。包括协议往返、加密、乱序分片、重传文件传输、真实 UDP 接收期限、音频背压、队列和会话测试。
- Web **11 项**自动回归通过，见 [web-tests.txt](web-tests.txt)。这些是可重复的接口测试；真实浏览器验证另列如下。
- 严格静态检查：`cargo clippy --workspace --all-targets -- -D warnings`，结果见 [clippy.txt](clippy.txt)。
- 本次改动的 Rust 文件通过 `rustfmt --check`，补丁通过 `git diff --check`。工作区仍有本轮未改动文件的历史格式差异，不能声称整个工作区 `cargo fmt --all --check` 已通过。
- macOS 原生冒烟：4 秒测试窗口收到 **103 个视频包、176 个音频包、1 份音频配置、3 份主机遥测**；legacy 音视频包均为 0。**65,536 字节**文件成功落盘，源与目标 SHA-256 一致，观察到 StopStream，发送错误计数为 0。见 [native-smoke.txt](native-smoke.txt) 与 [native-proof.json](native-proof.json)。包数不是渲染 FPS，音频包到达也不是扬声器回放验收。
- 浏览器真实验证：用 FFmpeg 生成的 **640×360、30 FPS HEVC 测试画面**，经本地测试网关送入实际 WebCodecs 解码；界面观测到 **28–29 FPS**。验证了连接拒绝、重连、断开、1280×720 与 390×844 布局。测试网关只发送生成的图案；这不等于原生 relay 与 Web 客户端的协议联调。

## 传输边界

- 正常单个 UDP 分片载荷最多 **1,400 字节**，分片数据报最多 **1,410 字节**。超限数据报会明确拒绝，避免截断后继续解析。
- 每条消息最多 **4,096 个分片**，即最多 **5,734,400 字节（约 5.47 MiB）**；同时保留最多 10 条未完成消息，2 秒过期。上限有意限制异常内存增长；极大关键帧需先测量大小再调整，不能把限制当成所有编码配置的保证。
- 20 ms 是重排期限，不包含操作系统调度、网络传输、解码和呈现时间。16 帧是内存与积压上限，正常有序流仍立即出队。

## 本轮以外的具体缺口

1. Web 仍需要原生 relay 协议适配。当前能验证的是完整 HEVC Annex B access unit 网关；发现、音频、剪贴板和文件通道尚未接入，界面已明确显示不可用。
2. Android `MediaCodecPlayer.kt` 的 HEVC 失败后改用 AVC，并未同步协商发送端码流；相关异常也被忽略。需要在有设备的环境里完成编解码协商和 Surface 生命周期验证。本轮不把共用核心测试算作 Android 实机验收。
3. `app/src/preferences.rs` 的保存仍共用固定 `.tmp` 路径，并且多处是读取后修改再保存；多个写入者可能互相干扰。后续应统一写入归属并验证并发更新语义。
4. Linux、Windows、Android 的真实采集、解码和输入设备未在本轮连接验证；macOS 解码格式失败路径有资源所有权修复和构建检查，但没有声称覆盖了所有驱动故障。

## 性能对照方法

使用原有 `loopback_transport_bench`，原始基线与修改版分别在独立 Cargo 目录构建 release 二进制。每种载荷每轮 15,000 次，交替运行前后版本各 5 轮；统计各轮平均单包耗时的中位数，单位为微秒。这是本机 UDP 回环吞吐成本，不是跨机器端到端呈现时延。原始输出与二进制 SHA-256 随最终结果保存。

早期共用 Cargo 产物目录的试验已作废，不用于验收或收益结论。独立构建对照及移除单个改动的试验确认：缩小接收缓冲到约 1.4 KiB 或 2 KiB 虽有大消息收益，却使小包回环耗时增加约 3 微秒；仅调整控制消息布局并非这个差异的来源。因此最终撤回小缓冲方案，保留原有接收缓冲布局。

本轮更明确的收益是：缺包等待不再依赖累积大量后续帧、队列和分片内存有界、空闲发送器不再持续轮询、故障与重连能释放资源，以及展示的数据有实际来源。
