## 结论

这组需求适合作为下一阶段的产品目标。目前是“一路桌面串流加旁路服务”的基础，尚不是支持多个独立窗口、双向发布和完整跨平台数据协作的产品。单窗口采集、多窗口接收、反向投屏和按应用音量控制都有可行的平台路径，但不能承诺所有操作系统均支持任意多个应用并行采集，或同一应用的每个窗口都能分离声音。

关键改造是把**设备连接、采集源、观看订阅和音频源**分开管理。这样才能让文件传输不依赖录屏、让隐藏窗口停流而其他窗口继续播放，并让同一设备同时观看和投屏。以下是设计和验收要求，不代表已经实现。

## 六项需求与当前差距

| 需求 | 当前代码 | 下一步必须补齐 |
| --- | --- | --- |
| 文件传输 | 桌面共享内核有分块、目录组、取消、CRC32 校验；发送端读完并入队后即发本地完成事件 | 接收确认、缺块重传、超时、断点续传、临时文件提交、最终哈希校验；Android 文件选择和接收目录；独立文件会话 |

| 指定应用窗口与多窗口音频 | macOS 当前采集主显示器；主机单活动会话；画中画复用同一画面 | 可授权源列表、原生窗口采集、多路独立订阅和解码、按应用音频采集、去重混音、本地音量控制 |
| 反向投屏 | 桌面角色模型将 Viewing/Serving 互斥管理 | 双向发布与订阅可并存，双方各自授权源；输入权限和方向独立；避免再采集播放画面和声音 |
| Android 支持观看与投屏 | 一个 MediaCodec 接收播放器；没有 MediaProjection 发布服务 | 多路接收和资源预算；另建系统授权的屏幕/单应用投屏源、硬编码和可用时的播放音频采集 |

“任意分辨率”应定义为用户可选择窗口大小、画面保持比例并自动适配；编码器实际尺寸还受对齐、最大尺寸和解码能力限制。不能把目标 FPS/码率等同于实际达到值，当前自定义 FPS 仍是正整数。

## 当前代码依据

路径相对于仓库根目录。

- `host/src/service.rs::run_host_service`：只有一组 `active_client_addr`、`active_session_id`、`active_settings_tx`；新的 StartStream 替换原活动串流。
- `remote_core/src/role.rs::RoleState`：Idle/Connecting/Viewing/Serving 是互斥枚举。
- `host/src/capture.rs`：选择主显示器并使用 `SCContentFilter::with_display`；尚无窗口选择协议。现有 ScreenCaptureKit 依赖具有 `with_window`、`with_including_windows`、`with_including_applications`，可用于后续实现，但不是当前产品功能。
- `app/src/ui.rs::presentation_frame`：主画面与画中画共享同一帧，不是两个独立源。
- `host/src/audio_capture.rs`：系统音频采用显示器过滤器，并排除当前进程音频；尚未按应用拆轨。Windows/Linux 当前音频主路径仍是默认输入设备，不能视为系统输出或按应用 loopback。
- `protocol/src/lib.rs::FileTransferControl`：只有 CancelTransfer/CancelGroup。`remote_core/src/file_transfer_runtime.rs::send_reader` 在读完本地文件后产生 OutgoingCompleted。调度器 Reliable 类别不能提供 UDP 可靠交付保证。
- `remote_core/src/file_transfer.rs::IncomingFileTransfer::finish`：检查分块数量、flush、CRC32；未形成 `sync_all` 加临时文件原子提交的持久化契约。
- `remote_client_bridge/src/lib.rs`：接收配置的 `clipboard_control` 和 `file_transfer_control` 为 None，Android 文件和剪贴板不能按“共享 Rust 内核存在”认定完成。
- `android/app/src/main/java/com/remoteplay/client/ui/MobileViewportScreen.kt`：仍只有一个 Surface/解码实例，初始请求和 codec 启动尺寸仍为 1920×1080。

## 连接和多路媒体的边界

建议逐步引入以下概念，并保留单流兼容路径；不要求一次重写整个传输层。

| 对象 | 职责 |
| --- | --- |
| 设备连接 | 认证、能力协商、路由、保活；可独立承载文件、剪贴板、输入控制 |
| 采集源 | 由发布端授权的显示器、窗口或应用；提供源标识、生命周期、实际尺寸及可用音频组 |
| 观看订阅 | 指向某个源；分别设置目标尺寸、FPS、码率、暂停/恢复；每路有明确的视频轨标识 |
| 音频源及订阅 | 按可分离的应用/进程或系统混音标识；多个画面可共享一条音频源 |
| 几何版本 | 绑定内容矩形、DPI、旋转、缩放及输入映射；旧尺寸的输入事件不能误投到新几何 |

设备 A 可向 B 发布窗口，同时订阅 B 的桌面。暂停某个订阅不能断开连接、关闭其他订阅或中断文件。采集源关闭、授权撤销和观看者取消订阅分别处理，不能复用一个全局 StopStream 承担全部行为。兼容性协商应明确单流旧端可用的功能，不能静默把选定窗口改成整个桌面。

远程输入需要绑定授权源和几何版本：共享窗口不自动意味着允许操作整个桌面。窗口移动、缩放、关闭或失焦后的输入必须按平台能力明确处理，并释放已按下的按键。各平台的窗口控制限制也要通过能力协商呈现。

## 多窗口的显示、声音与性能规则

### 可见性决定视频订阅，焦点决定输入目标

- 分屏、平铺或画中画中同时可见的窗口都继续串流，不因没有键盘焦点而暂停。
- 被切走的标签页、最小化窗口和用户明确暂停的画面可停视频。短时保留连接与可复用资源，恢复先取关键帧，清除旧帧队列。
- “隐藏后继续听声音”需要独立选项。用户选择音频继续时，只暂停视频；不应将音频与视频硬绑为一种暂停状态。
- 长时隐藏可释放采集/编码/解码资源；这是资源释放与恢复时延的取舍，应分别记录热恢复、冷恢复耗时。
- Android 观看端退后台适用观看暂停策略；Android 投屏源退后台通常意味着用户正在使用被分享的 App，必须继续用户已授权的投屏。长时断连策略还必须考虑正在传文件、对外投屏、对讲和音频播放，不能仅以 Activity.onStop 作全局判断。

### 按真实音频源调音量

应用/进程是常见的最小可分离音频来源，窗口通常不是。一个浏览器的多个窗口或标签页不一定能独立采音。相同应用的多个画面应关联同一音频组，只采集和播放一次，音量控件联动并提示来源；只有平台确实提供独立源时，才启用真正的单窗口音量。

播放端音量默认只影响本地播放，不改变源机器系统音量。每源静音、增益和左右声道处理应在接收混音中完成。系统混音与已单独采集的应用音频不能重复叠加；双向投屏应排除自身播放音频和画面，无法排除时要明确可用模式，避免声反馈和无限套娃。

### 尺寸和资源预算

保持源内容比例，默认适配显示区域并留边；裁剪或拉伸由用户显式选择。编码对齐填充不能成为黑边输入区。源尺寸、旋转和 DPI 更新时同步刷新画面与输入映射，禁止用旧比例继续发送拖拽坐标。

布局变化先即时调整显示，再对编码尺寸更新去抖和量化，避免拖动分隔线时不断重建编码器。缩略窗口按可见像素和用户目标降低分辨率/FPS，不让每个小窗口都默认 1080p60。共享相同源和兼容配置的观看者可以复用采集/编码，但必须先验证平台能力和收益。

为每设备设置总像素率、编码器/解码器数量、带宽和内存预算；超出预算时降低次要窗口质量并显示原因。保留最近帧、有界队列、及时丢弃过期帧；文件传输需要背压和公平调度，不能挤占音频、控制和关键帧。

## 平台能力边界

| 平台 | 单窗口/应用画面 | 应用声音 | 多窗口与反向投屏的实际边界 |
| --- | --- | --- | --- |
| macOS | ScreenCaptureKit 提供窗口/应用过滤；当前尚未接入产品选择 | 可按应用过滤，需验证系统版本、进程归属和音轨去重 | 最适合先完成原生多流闭环；窗口关闭、遮挡、最小化的行为须单测，不能靠桌面裁剪冒充窗口隔离 |
| Windows | 应新增原生窗口采集后端，当前 gdigrab 主要为桌面路径 | 官方进程 loopback 示例要求 build 20348+；不能假定所有 Windows 10 都具备 | 还需补观看端 GUI、真正解码/渲染及音频输出，再验收双向功能 |
| Linux | 需面向桌面环境接入 portal/PipeWire 等授权路径；当前主要是 X11/KMS FFmpeg | 需要 PipeWire/PulseAudio 节点路由及权限/环境验证 | Wayland、X11 与不同音频服务不能按同一种后端承诺；原生观看端也未补齐 |
| Android 观看端 | 多个接收 Surface/解码器在架构上可行 | 可对接收音轨分别设本地音量 | 受硬件解码实例和总像素率约束，需真机预算与降级 |
| Android 投屏端 | 官方 Android 14/API 34 文档提供用户选择单应用分享，实际入口随设备系统实现；全屏用 MediaProjection | Android 10+ AudioPlaybackCapture 可按 UID 过滤，但须满足源应用策略、用途、授权和同用户资料等条件 | 普通应用不能承诺同时独立采集任意多个 App；多个远端窗口的接收显示不受这项源采集限制 |

Android 每次新的投屏会话需用户授权；Android 14 起不能重用同一个授权 Intent，不能对同一 MediaProjection 实例多次 createVirtualDisplay。必须配置 mediaProjection 类型前台服务及对应权限，响应系统停止、锁屏等终止事件。旋转或源窗口尺寸变化使用 `onCapturedContentResize()` 更新，不应误创建新的投屏会话。暂停后能否复用取决于投屏授权是否仍有效；已被系统终止时不能承诺无感恢复。

投屏不自动授予手机控制权限。Android 远程操作需要单独设计受支持、由用户启用的控制能力；不能从 MediaProjection 权限推导任意输入注入。

Android 10+ 的剪贴板读取受前台焦点或默认输入法身份限制，前台服务不等于可以无限制后台读取。产品应支持在可访问时同步，或由用户主动粘贴/分享；不能承诺始终后台双向监听所有格式。图片和文件需处理 Content URI 的读取授权与生命周期。

## 文件和剪贴板优先补齐的语义

1. **发送进度与送达结果分离。** 本地读完不是对端成功；只有接收端完成校验并按约定提交文件后的 ACK 才显示成功。终态确认也要可重试、幂等，避免 ACK 丢失导致误报或重复文件。
2. **先可靠收发，再扩大文件剪贴板。** 补齐缺块请求、限速补传、超时、取消、重连续传及临时文件清理。发送过程中源文件变化应被发现并报告；重名、磁盘满、权限失败不得静默覆盖或显示成功。
3. **不要求先开画面。** 文件与剪贴板通过独立授权的设备连接工作；没有录屏权限也能传文件。后台媒体省电策略不能中断仍活动的传输。
4. **剪贴板不广播到所有画面。** 同步目标采用用户选定设备；多个可见窗口不等于所有对端同时接收。携带来源/对象标识并抑制回写回环。
5. **支持可协商的格式集合。** 文本、图片、文件分别表达 MIME、大小和能力；文件引用不能当作另一台设备可用的本地路径。HTML/RTF 等可后续扩展，不承诺任意私有剪贴板格式跨平台无损。普通文件下载是否写入剪贴板应由动作意图决定，不能收到文件就覆盖本地剪贴板。

## 推荐实施顺序与完成条件

| 阶段 | 范围 | 必须看到的验收结果 |
| --- | --- | --- |
| 1：连接与文件可靠性 | 独立认证连接、能力协商、可靠文件传输、接收端提交确认；Android 文件入口 | 无录屏权限仍可双向传文件；目录、大文件、零字节、中文名、取消、断连、磁盘满有明确结果；在丢包/乱序/重复与 ACK 丢失下最终哈希一致，资源有界，不假成功 |
| 2：跨平台剪贴板 | 文本→图像→文件，按平台能力逐步补齐；和文件模块共用可靠交付 | 双向粘贴内容正确；切换目标不会泄漏到其他设备；无回环；Android 受限状态可理解，URI 权限失效可报告 |
| 3：macOS 单窗口到多窗口及双向 | 源枚举与授权、每路媒体标识、多个订阅/播放器、双向角色、每路暂停和几何版本 | 两台物理 Mac 同时显示至少 3 路不同窗口；隐藏一窗仅该路媒体归零；切换恢复正确；同时反向投屏；移动/缩放/关闭窗口时控制不串窗 |
| 4：按应用声音 | 应用音轨归组、本地增益/静音、去重混音、反馈防护 | 同应用多窗只播放一次；不同音源音量独立；隐藏继续听、恢复音画同步均通过；不支持的分离能力明确显示 |
| 5：Android 多路观看及投屏 | 多解码布局与预算；MediaProjection 源、硬编码、合规的应用音频采集；区分观看/发布生命周期 | 真机横竖屏、分屏和不同尺寸输入正确；超解码预算可降级；投屏时切到被分享 App 不停止；用户停止/锁屏/授权撤销可正确结束；应用音频拒绝时准确反馈 |
| 6：Windows/Linux 对齐及跨网络验收 | 原生采集/播放/音频后端、平台控制与剪贴板差距；长后台按需推送唤醒 | 每个声明支持的系统版本和设备方向分别完成实际画面、声音、控制、文件与恢复测试；LAN/P2P/中继、Wi-Fi/蜂窝分开记录 |

阶段 3 先以单个授权窗口闭环，再扩展多路，避免同时更换协议、平台后端和 UI 而无法定位问题。Windows/Linux 被控兼容性应在每阶段回归，不能留到最后才发现基础协议不兼容。

性能验收需固定设备、系统版本、源内容、网络和负载，记录实际呈现 FPS、首帧与恢复 p50/p95/p99、采集/编码/排队/解码耗时、音画偏差、丢帧、CPU/GPU、内存、温度及真机功耗。分别比较 1/2/4 路可见、部分隐藏和全隐藏，观察总像素率与质量预算。已有同机采集到解码测试不能替代两台物理设备的实际显示/声音验收，也不能支持“性能已到极致”的结论。

Android 长后台可按市场选择 FCM/厂商共享推送，减少应用自建保活；这仍未接入。共享推送不是即时必达控制通道，也不替代投屏授权。后台保持连接是否值得，应以 Wi-Fi/蜂窝真机对照功耗和恢复时延决定，而非只看载荷字节数。
