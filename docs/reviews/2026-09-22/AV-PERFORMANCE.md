## 本轮音视频修改

- macOS 编码器使用 SDK 的 `kVTEncodeFrameOptionKey_ForceKeyFrame`。原来的字面量 `ForceKeyFrame` 不是实际参数值，系统忽略后会导致恢复请求无效，等待约 10 秒的周期关键帧。关键帧附件也改为读取 `NotSync` 的布尔值。
- 视频发送队列的 16 毫秒预算从入队时计算，保留紧凑协议的期限表示范围。原来从采集时刻计算，会让启动阶段和较慢的关键帧编码尚未进入发送队列就过期。
- 共用接收器在初始关键帧缺失、序号断点、解码队列溢出或解码失败时，沿原连接请求关键帧；每 250 毫秒重试，停止会话后结束请求。没有新增 wire 协议。
- 原生解码队列从 200 帧缩到 8 帧。开始播放、切换会话或预测链断裂时等待关键帧；释放旧 IOSurface 时不占用共享帧锁。
- 系统声音和远端麦克风按同一输出时钟混合，替代原来的串行拼接。每路 PCM 缓冲限制为 60 毫秒，溢出保留最近的完整声道帧；回调去掉共享余量锁与反复的头部搬移。
- Opus 按实际输出设备采样率解码，避免源采样率与设备不同造成速度、音调错误；复用解码缓冲，重复的音频配置不再重建解码器，抖动缓冲可以按定时器释放。
- 音频分块共用一次 `drain`，只搬移一次未完成尾部，消除突发大批次的反复搬移。没有增加依赖。

## 测量口径

测试机为 Apple M2 Max / Mac14,6，macOS 26.5，Rust 1.94.1。请求 1920×1080、60 FPS、8 Mbps，采集当前本机桌面，经过 UDP 和真实 VideoToolbox 解码。Release 使用优化构建；Debug 对照单独列出。性能测试期间没有并行执行本任务的编译、其他播放探针或微基准。

`playback_probe` 观察实际 CVPixelBuffer。采集到解码延迟使用同机时间基准，并扣除探针轮询等待；“稳态”排除开头两秒，全程指标仍包含启动。丢包脚本在第 4 秒开始丢弃 100 毫秒的视频数据，音频和控制继续转发。播放间隔包含这段人为丢包时间。

这些数值不是跨公网、双机或屏幕显示延迟。探针静音，避免本机回授，因而不证明扬声器听感、音画同步或实际 GUI 扫描输出；当前桌面负载也不能代替高运动画面、4K、高帧率、功耗或长时间耐久测试。

## 视频结果

视频恢复修复前的 15 秒 Debug 探针，首帧为 **10,608 ms**、解码 262 帧；修复后的 Debug 探针首帧为 **1,106 ms**、解码 782 帧、解码错误为 0。前者直连本机，后者经过本机代理；该对照用于确认首帧与恢复故障，不用于声称编码器吞吐提升三倍。

最终代码的 Release 结果：

| 指标 | 连续 60 秒 | 注入 100 ms 丢包，运行 15 秒 |
| --- | ---: | ---: |
| 实际解码尺寸 | 1920×1080 | 1920×1080 |
| 首帧 | 1,101 ms | 1,115 ms |
| 解码帧数 | 3,230 | 725 |
| 稳态观察帧率 | 54.81 FPS | 51.15 FPS |
| 解码错误 | 0 | 0 |
| 稳态最大播放间隔 | 66.34 ms | 173.85 ms |
| 稳态采集→解码 p50 / p95 / p99 | 11.67 / 13.45 / 14.82 ms | 11.55 / 13.62 / 16.86 ms |
| 实际人为丢弃 | 无 | 5 帧、41 个 UDP 数据报 |

连续测试没有超过 100 ms 的播放间隔。丢包测试出现两次超过 100 ms 的间隔，最大值如表所示；不能把全部抖动都归因于注入事件。此前三次独立丢包测试均为零解码错误，最大间隔为 141–161 ms；它们在音频分块最后一次调整之前运行，最终复核使用上表数据。

**60 FPS 尚未稳定达到，首帧仍约 1.1 秒。** 最终连续测试结束前的发送端遥测也只有约 53 FPS，仍需进一步剖析采集、编码及调度，使用可控运动画面区分内容变化、负载和真正的性能瓶颈。当前结果不支持“已经达到极致”的结论。

逐次数据和验证状态保存在 [av-results.json](av-results.json)，包括不排除启动的全程延迟分布；启动期间仍有队列丢弃，因此不能只看稳态延迟。原始日志附在同目录 `av-*.log`，它们受仓库日志忽略规则影响，不会自动进入 Git。
