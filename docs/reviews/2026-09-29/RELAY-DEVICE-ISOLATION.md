# Relay 设备错投、返回地址覆盖与桌面输入修复

## 现场与证据

用户在 HO5 能看到画面后反馈键鼠无效、应用投屏失败，以及依次连接 Mac Studio / MacBook 时画面来源疑似不对应。最新句子单独理解存在歧义，但现场代码与隔离复现确认了一项独立成立的严重错投问题，不能归因于用户操作。

旧 Relay 服务在同组广播 Data；每个终端只有一个 control tunnel，发现列表把所有 Relay 设备映射到同一本地 UDP 地址。tunnel 又把返回目标改为最后一次发送数据的本地客户端。结果是点击某台设备会把请求送给同组多台主机，之后建立的连接会抢走前一连接的回包。

Mac Studio 上运行的真实三节点 WebSocket 复现使用纯合成数据，没有采集画面或注入输入。结果：选择 Studio 的请求到达 2 台模拟主机，发给第一个客户端的回复确实到达第二个客户端。首次测试误把 WebSocket 连到普通 TCP 测试监听器，未形成证据；改用生产的 WebSocket 监听器后稳定复现。

另外，真实已安装且正确签名的 Mac Studio alpha.4 经隔离可视测试窗口验证：主屏解码 39 帧；窗口实际收到鼠标点击及单个按键；切换到该窗口后解码 16 帧、零解码错误。该测试仅在确认测试窗口拿到点击和焦点后发送按键，不对其他应用键入。它证明 Studio 本机输入和窗口采集可用，不代表 HO5 的完整 GUI 操作已验收。

## 共享核心修复

新增 `remote_core::routed_relay`，桌面三平台与 Android 复用同一实现，不为每种 OS 各写一套网络路由。

- 发现仍可广播，但为每个目标设备分配独立的本地入口。
- 每个本地连接增加随机 128 位连接 token；远端为来源设备和 token 分配独立的主机返回通道。
- 传输信封绑定源设备、目标设备、方向和连接 token，并用从既有网络凭据派生的 HMAC 校验。底层会话加密继续保留。
- 非本机目标、未知返回 token、错误来源、错误网络以及旧的裸广播控制数据一律丢弃，不猜目标、不接到“第一个能回应的设备”。
- 控制数据迁入 `control-device-v1` 命名空间，避免旧版主机把新版信封当作控制包。旧新版 Relay 必须配套更新；不能以不安全广播兼容方式兜底。
- peer/连接/队列均有上限，空闲连接清理，任务退出关闭所属监听器。
- 现有 NAS Relay 仍转发不透明包，无需停服升级；它仍可能广播已经加密并带目标绑定的包，非目标端会在进入业务主机前丢弃。本轮不是服务端按目标单播带宽优化，也不宣称组内共享密钥等于每设备独立公钥认证。

## 输入与 GUI 修复

此前只要两秒没有新解码帧，can_input 就返回 false。静止桌面本来可以不产生新帧，因此会把正常画面误判为不可控。现在保留“当前来源至少收到一帧”的要求，改用鉴权连接心跳判断存活；真正连接失联、暂停、来源未确认和旧来源帧仍禁止控制。

默认只看策略保留，但 Input locked 复选框改为明确的 Enable control / Lock control 按钮；底部说明只读、等待首帧、暂停、心跳超时或已启用。应用窗口当前保持只读，不把其坐标错误投到主屏。

异步建立连接完成时只遵循用户最新选中的设备意图，不由最后返回的请求抢焦点；关闭前面的标签时保留原选中设备；纹理标识增加连接实例 ID，状态行显示设备与连接编号。

## 安全与验收边界

旧版 Relay 会话在升级前保持输入锁定，不对不确定目标键入或发送私密文件。升级必须使用原 macOS 签名身份及新安装器；不修改 TCC、不重新入网、不启用 Windows 主机采集、不改 UU/Remote Hosts。

本轮 App 投屏按设备列表中的应用窗口来源验收。Android 屏幕反向推送、任意应用窗口的远端键鼠控制、所有 LAN/P2P 方向的长期并发压力验收是不同边界，不可用本轮局部测试替代。
