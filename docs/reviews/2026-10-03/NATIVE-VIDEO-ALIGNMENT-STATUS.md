# 原生视频扩展：对齐与性能阶段记录

## 用户确认与实施边界

用户回复“可以重点是对齐和性能”，明确批准固定版 GPUI 最小原生视频扩展方案。优先对齐原 UI、功能行为以及视频/输入坐标，并以实际性能验收。无需再次要求用户批准同一范围；Flutter、替换其他图形依赖、改变线上协议或删除功能仍不包含在此批准内。

## 这次真正完成的内容

在未接入产品依赖的 third_party/gpui-ce 副本中编写共享几何/色彩规则，以及 Windows D3D11 原生视频合成草稿。已有 GPUI、网络、会话和原 UI 源文件未切换到该副本。

共享规则覆盖 coded extent 与 visible crop 的区别、像素宽高比、0/90/180/270 度旋转、等比适配/裁切/拉伸、黑边拒绝输入、负坐标和不同 DPI。采样变换与输入逆变换使用同一约定，避免屏幕尺寸、填充区域与远端输入位置各算一遍。

色彩规则显式区分 BT.601/BT.709、8位NV12/高位对齐10位P010、全范围/视频范围；不把10位信号按普通16位强度解释。它是 SDR 规则，不伪装成 HDR、任意色域或系统色彩管理完整支持。

线性 NV12 DMA 平面元数据校验覆盖 stride、offset、对象大小、溢出与重叠。该检查不表示Linux驱动已导入真实DMA-BUF，也不能把线性规则套给带modifier的平铺资源。

## 已执行的验证

使用 rustc 在 MacBook 上单独编译并执行 std-only 公共模块测试，16项通过、0失败、0忽略。包含4096组确定性生成的旋转、缩放、裁切和DPI布局；其中3571个点落在有效画面内，并验证其采样位置与输入位置一致。其他点明确被判为画面外。此结果是几何/色彩和边界测试，不是GPU呈现或实体键鼠验收。

## Windows 草稿的性能约束

D3D11原生资源以拥有生命周期的对象承载，检查GPU适配器、格式、尺寸和共享同步约束；导入/SRV缓存按稳定资源身份复用。草稿限制导入缓存和在途GPU查询数量，不建立无限队列。只有144字节参数缓冲映射，不在生产合成路径映射整幅视频或做CPU色彩循环。

共享资源的AcquireSync使用零超时；特别处理其WAIT_TIMEOUT/WAIT_ABANDONED返回值，不能把windows-rs丢失状态值后的Result::Ok等同“拿到资源锁”。GPU event查询也区分S_OK和S_FALSE。统计明确区分提交与GPU完成，不声称GPU完成就是显示器呈现。

这些只是已写的实现草稿，Windows编译及物理GPU测试均未执行。已准备的GPU测试会读取小型离屏验证目标以检查像素，测试输入一次性生成；这不是产品播放路径中的CPU读回，也不能用它证明实际解码零拷贝。代码审查还记录了Windows BOOL绑定及资源退休边界需在编译/硬件联调时继续核对，不能直接用于发布。

## 为什么没有接入或发布

最初复制固定GPUI源码成功，但读取缓存中的.cargo-checksum.json失败；该缓存没有这个文件。于是后续的来源清单、Cargo备份和依赖patch都没有创建。后续尝试通过Cargo锁定校验与缓存crate验证完成接入的整条工具调用，被平台安全检查拒绝，没有执行。未通过别的工具、设备或改写命令重试这个接入操作。

实际复核：根Cargo.toml没有patch.crates-io；app未声明gpui-native-video；副本native_video模块也未在库根导出，固定来源清单未生成。不能写“固定版扩展已接入/已编译”。现有产品不引用这份草稿。后续只继续了独立数学/元数据边界验证，不触碰被拒绝的依赖接入操作。
